# ADR Policy

Architecture Decision Records (ADRs) are the primary mechanism for documenting significant technical decisions in Itqahn.

---

## When ADRs Are Required

An ADR is **required** for:

| Decision Type | Examples |
|---------------|----------|
| Technology selection | Database, framework, language, cloud service |
| Architectural patterns | Microservices vs monolith, event-driven vs request-response |
| API design | REST vs gRPC, versioning strategy, authentication method |
| Data model changes | Schema design, normalization decisions, storage format |
| Security decisions | Encryption approach, auth flow, trust boundaries |
| Integration approach | Direct API vs MCP, sync vs async, polling vs webhooks |
| Infrastructure choices | Container orchestration, networking, observability stack |
| Breaking changes | Deprecations, migrations, backward compatibility |

An ADR is **not required** for:
- Bug fixes
- Minor refactoring (no behavior change)
- Dependency version updates (unless major version)
- Documentation changes
- Configuration changes (unless security-relevant)

---

## ADR Format

All ADRs must follow the template at `templates/engineering/ADR.md`:

```markdown
# ADR-XXXX: [Title]

## Status
[Proposed | Accepted | Deprecated | Superseded by ADR-YYYY]

## Context
[What problem are we solving? What constraints exist?]

## Decision
[What did we decide? Be specific.]

## Options Considered
### Option A: [Name]
- Pros: ...
- Cons: ...

### Option B: [Name]
- Pros: ...
- Cons: ...

## Consequences
### Benefits
- ...

### Costs
- ...

### Risks
- ...

## Related
- PRD: [link]
- Other ADRs: [links]
- External references: [links]
```

---

## Naming Convention

ADR files must follow this naming pattern:

```
docs/99-appendix/adrs/ADR-XXXX-short-title.md
```

Where:
- `XXXX` is a zero-padded sequential number
- `short-title` is lowercase, hyphenated, max 50 characters

**Examples:**
- `ADR-0001-use-temporal-for-orchestration.md`
- `ADR-0002-postgresql-as-primary-database.md`
- `ADR-0003-spiffe-for-workload-identity.md`

## ADR Lifecycle

```
┌──────────┐    Review    ┌──────────┐    Time/Change    ┌────────────┐
│ Proposed │─────────────▶│ Accepted │──────────────────▶│ Deprecated │
└──────────┘              └──────────┘                   └────────────┘
                               │
                               │ New ADR
                               ▼
                          ┌────────────────┐
                          │ Superseded by  │
                          │   ADR-YYYY     │
                          └────────────────┘
```

### Status Definitions

| Status | Meaning |
|--------|---------|
| **Proposed** | Under discussion, not yet approved |
| **Accepted** | Approved and in effect |
| **Deprecated** | No longer recommended, but not replaced |
| **Superseded** | Replaced by a newer ADR (must link) |

---

## Immutability Rule

**ADRs are immutable once accepted.**

- Do not edit the content of an accepted ADR
- Do not delete ADRs
- To change a decision, create a new ADR that supersedes the old one
- Update only the `Status` field to mark as deprecated/superseded

This ensures the decision history is preserved for audit and learning.

---

## Approval Process

### For Standard Decisions

1. Author creates ADR in `Proposed` status
2. Author opens PR with ADR
3. Required reviewers (based on CODEOWNERS):
   - Relevant architect (Backend, Frontend, Data, etc.)
   - At least 1 other engineer
4. Discussion in PR comments
5. Once approved, status changes to `Accepted`
6. PR merges

### For Security-Relevant Decisions

Additional reviewers required:
- Security team (Threat Modeler or AppSec Reviewer)
- For auth decisions: CISO approval

### For Infrastructure Decisions

Additional reviewers required:
- Platform Engineer
- SRE Commander
- For cost-significant changes: CFO FinOps

## Discovery

To find relevant ADRs:

1. **By topic**: Search in `docs/99-appendix/adrs/`
2. **By status**: Filter decision log by status
3. **By date**: Sort decision log by date
4. **By service**: Check service README for linked ADRs
5. **By PRD**: PRDs link to related ADRs

---

## Anti-Patterns

Avoid these common ADR mistakes:

| Anti-Pattern | Problem | Fix |
|--------------|---------|-----|
| **Too vague** | "We decided to use a database" | Specify which database and why |
| **No alternatives** | Only one option listed | Always document 2+ options considered |
| **Missing consequences** | No risks or costs listed | Be honest about tradeoffs |
| **Premature deprecation** | Deprecating before new approach is proven | Keep old ADR until replacement is stable |
| **Orphan ADRs** | Not linked from relevant docs | Always cross-reference |
